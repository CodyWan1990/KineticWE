## Release 7 Status

The current spec contains:

- `Release: 7`
- The confirmed launcher and configuration fixes
- Weak recommendations for optional desktop tools
- The greeter ownership fix
- The portal locale and logging-category conflict fix
- Final install guidance in `%posttrans`

The release 7 SRPM has been generated. Binary RPMs and installation testing
remain to be completed.

The purpose of release 7 is to package the confirmed launcher and dependency
changes and to prevent the KineticWE portal from conflicting with Fedora's
standard KDE portal.

Release 7 also fixes the installation failure found in its earlier build. The
`%posttrans` scripts ran `rpm -q` while RPM already held its transaction lock.
Release 7 uses file checks and package-specific messages instead, so the
scriptlets do not start a nested RPM query.

## Dependencies

The main package requires the core runtime needed by the session, including:

- `adw-gtk3-theme`
- `plasma-breeze`
- `plasma-breeze-common`
- `breeze-icons`
- `xdg-desktop-portal`
- `xdg-desktop-portal-kwe`
- `xorg-x11-server-Xwayland`
- `systemd`
- `bash`

The following are recommended, but are not required to install KineticWE:

- `alacritty`
- `qt5ct`
- `qt6ct`
- `spectacle`

The main package requires matching versions of `kineticwe-noctalia` and
`xdg-desktop-portal-kwe`. This makes a normal upgrade update the required
subpackages together with the main package. If `kineticwe-greeter` is already
installed, it also requires the matching main package.

This does not replace an older broken `0.0.1-7` with a different build that has
the same version-release. RPM considers those builds the same package. Users
with that package already installed must explicitly reinstall it and the
installed subpackages.

Qt5 and Qt6 Plasma integration was not selected because it would pull in a
large Plasma dependency chain. KineticWE continues to use `qt5ct` and `qt6ct`
as optional tools.

`adw-gtk3-theme` remains required because the GTK templates select that theme.
The package must be present on a fresh install or GTK applications may fall
back to a missing theme.

What this means: the required list contains packages needed for the session to
operate, while the recommended list contains useful applications that users may
choose not to install.

**What changed:** the optional desktop tools use `Recommends:` instead of
`Requires:`.

**Why:** KineticWE should not fail to install or remove because a user does not
want a terminal, screenshot tool, or Qt configuration tool.

**How:** The spec keeps core session packages in `Requires:` and puts
`alacritty`, `qt5ct`, `qt6ct`, and `spectacle` in `Recommends:`.

## Session And Theming Fixes

The packaging-local session launcher:

- Keeps compositor settings in `~/.config/kineticwe`.
- Keeps normal applications on the normal XDG config paths.
- Preserves existing Qt and QML search paths.
- Seeds Qt settings in the user's resolved config directory.
- Preserves existing data and application search paths.
- Keeps GTK, KDE, and Qt theme settings aligned.

Why these changes are needed: the compositor uses a private config directory,
but applications launched inside the session must see the user's normal Qt,
GTK, and KDE settings. Replacing those paths caused applications to miss their
settings or use a different theme.

How the fix works: the launcher gives the compositor its private paths only at
startup and preserves the existing system and user search paths for other
applications.

The launcher also creates minimal `qt5ct` and `qt6ct` configuration files only
when they do not already exist. Those files point to Noctalia's generated color
scheme, so existing user settings are not overwritten while new installations
get a working theme.

The unresolved Dolphin/Konsole issue is limited to one Kinetic Settings or KWin
shortcut path. The same applications use the expected theme when started from
Noctalia. An earlier environment patch did not fix this and was removed.

## Portal Conflict Fix

The KineticWE portal was based on the KDE portal and originally used KDE file
names. That conflicted with the stock KDE portal package.

What was wrong: the two packages produced files with the same names.

Why it matters: RPM rejects the installation when two installed packages claim
the same locale or logging-category file.

During `%prep`, the release 7 spec changes the KineticWE portal names to:

- `xdg-desktop-portal-kwe.mo`
- `xdp-kwe.categories`

The main package excludes these files. The
`xdg-desktop-portal-kwe` subpackage owns them. This should allow both portal
packages to be installed together without file conflicts.

This is a packaging-time fix. It does not change the upstream source checkout.
It still needs to be verified with a release 7 build and install transaction.

How it works: the spec renames the files during `%prep`, excludes them from
the main package, and assigns them to `xdg-desktop-portal-kwe`.

The important distinction is:

- **Long-term design:** both portals can be installed together because their
  backend names, D-Bus services, portal metadata, locale files, and logging
  category files are separate. Each desktop session selects its own backend.
- **Release 7 implementation:** the spec applies text substitutions to the
  current source layout during `%prep`. This is expected to work for the
  current pinned source, but it is not yet build-tested and could need updates
  after a source sync.

The portal source changes are intentionally out of scope for the build-script
work. They will be managed separately. The current packaging workaround remains
in the spec `%prep` section.

## Greeter Fix

The greeter source is pinned to:

```text
b3e3bc0268fc5aaf346a250faac70570d15e3bef
```

**What:** The greeter tmpfiles configuration uses `greetd:greetd`.

**Why:** Fedora's greetd service uses the `greetd` account. The upstream file
used a generic `greeter` account that is not present on this system.

**How:** The spec changes the account and group names while installing the
tmpfiles configuration.

Install guidance is emitted from `%posttrans` so the user sees it after the
whole transaction has completed, rather than in the middle of package setup.

## Build Script

`build-rpms.sh` currently:

1. Checks the container, spec, and output paths.
2. Uses the Fedora 44 `kineticwe-build` container.
3. Installs build dependencies from the spec.
4. Creates the main source archive from committed Git `HEAD`.
5. Downloads or reuses valid pinned source archives.
6. Copies packaging-local files.
7. Builds the SRPM and, when requested, the binary RPMs.

Cached archives are checked before reuse, and download timeouts prevent a slow
source server from making the build appear stuck.

Why this matters: the build uses several large external archives. Reusing a
valid cache makes rebuilds faster, while timeouts make network failures visible
instead of appearing to be a stalled build.
